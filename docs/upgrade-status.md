# Web upgrade verification — staged implementation history

The integration and deployment status is superseded by [the 3 October release](release-20261003.md). The entries below document the earlier staged implementation.

## Implemented

- Shared navy/blue theme, consistent surfaces and controls, focus outlines, reduced-motion support.
- Password visibility toggle and registration password guidance.
- Offline notice that updates on connection changes.
- Read request timeout: 30 seconds; write request timeout: 120 seconds.
- Identical concurrent evaluation requests share one network submission. No automatic write retries.
- Existing local draft recovery and explicit retry flows remain intact.
- Result comparison against the preceding saved attempt of the same test type.
- Practice benchmark labels distinguish attempts from candidates; valid sample / total counts are shown when the backend provides them. Empty comparisons and missing averages do not imply low scores, and outdated comparison responses are ignored. Graphs are preserved.
- Mobile profile-grid and analytics-column overflow fixes.
- Sample-data, non-interactive signed-in previews generated by `PPDT_UI_SNAPSHOTS=1` when running app tests. Previews are ignored by Git and must not be deployed.

## Verification scope

The 11 preview routes (dashboard, practice, history, analytics, guide, profile, and all five test setup screens) were checked for horizontal overflow at 390, 820, and 1280 pixels. These previews use mocked account data; they do not validate live authentication or submissions. Automated tests cover interactive practice flows and result rendering.

## Requires approved content or backend work

- Password reset/session security: local backend reset-request/reset-completion and refresh endpoints now exist. Activation needs the session-check migration, Supabase email delivery/template setup, backend rollout, and web recovery/refresh integration. The web does not yet consume refresh credentials; do not store long-lived refresh tokens in localStorage or expose recovery secrets in query parameters/logs.
- Paginated history/lifetime totals and durable background evaluation jobs are implemented locally in the backend, but require their migrations, rollout and web integration. Background jobs also require a separately supervised worker.
- Benchmark metadata: backend corrections are implemented locally and need rollout. The updated web handles older responses with an explicit sample-details-unavailable notice. No additional benchmark migration is needed.
- Shared rate limits: local backend protection now shares database counters across API instances and adds verified-account and email-target budgets. Activation requires the counter migration, a common private hash secret, trusted-proxy configuration and backend rollout. The web still never automatically retries evaluation POSTs.
- Terms/privacy/research: the local backend now supports immutable approved policy versions and server-timestamped acceptance receipts. The web loads a published bundle and submits exact versions after explicit unchecked opt-in. Stale policies clear consent and reload; outages block signup without blocking sign-in. The owner must still supply approved text, versions, approval timestamps and effective dates before enabling signup enforcement. No policy text is seeded or invented as approved.
- Acceptance rollout: apply the policy migration, publish approved documents, deploy API/web, update mobile clients, then enable signup enforcement. Older clients remain compatible while enforcement is off, without fabricated versioned records. Existing-account status/reacceptance APIs exist but an existing-account prompt/feature gate is not yet implemented. See the backend's `docs/policy-acceptance.md`.
- Durable idempotency: the backend now has account-scoped submission receipts and an atomic attempt/receipt database migration. The web preserves its submission key through failed requests, reloads and token refreshes. Apply and verify the backend migration, then deploy the backend to activate this protection. No automatic POST retries are enabled. See the backend's `docs/evaluation-idempotency.md` for rollout and pending-request recovery details.

No live practice attempts were submitted, no account was created, and no backend deployment was performed during these checks.
